# System Design — ระบบสั่งพิซซ่าออนไลน์

## 1. ขอบเขตของระบบ

| ผู้ใช้ | สิ่งที่ทำได้ |
|---|---|
| ลูกค้า | ดูเมนู เลือกขนาด/ท็อปปิ้ง ใส่ตะกร้า ใส่โค้ดส่วนลด สั่งซื้อ ติดตามสถานะ ให้คะแนน |
| พนักงานหน้าร้าน | รับออเดอร์หน้าร้าน/โทรศัพท์ ค้นหาลูกค้าจากเบอร์ รับชำระเงิน |
| ครัว | เห็นคิวออเดอร์ เปลี่ยนสถานะ กำลังทำ → พร้อมเสิร์ฟ |
| คนส่ง (rider) | เห็นงานที่ได้รับมอบหมาย กดยืนยันส่งสำเร็จ |
| ผู้จัดการ/แอดมิน | จัดการเมนู ราคา โปรโมชั่น สต๊อกวัตถุดิบ ดูรายงานยอดขาย |

**สิ่งที่ระบบไม่ทำ:** ไม่ตัดบัตรเครดิตจริง (บันทึกสถานะการจ่ายอย่างเดียว) และไม่คำนวณเส้นทางส่งอาหาร

## 2. สถาปัตยกรรมภาพรวม

```
┌────────────────────┐   ┌────────────────────┐   ┌────────────────────┐
│  หน้าเว็บลูกค้า      │   │  หน้าจอพนักงาน      │   │  จอครัว / rider     │
│  index.html         │   │  admin.html        │   │  (แชร์ admin.html)  │
└─────────┬──────────┘   └─────────┬──────────┘   └─────────┬──────────┘
          │  fetch() JSON          │                        │
          └────────────────────────┼────────────────────────┘
                                   ▼
                    ┌──────────────────────────────┐
                    │      REST API (Express)       │
                    │  ┌────────────────────────┐  │
                    │  │ middleware: CORS,      │  │
                    │  │ JWT auth, role guard,  │  │
                    │  │ error handler          │  │
                    │  ├────────────────────────┤  │
                    │  │ routes → business logic │  │
                    │  │ (คิดราคา ตัดสต๊อก)      │  │
                    │  ├────────────────────────┤  │
                    │  │ data access layer      │  │
                    │  │ (connections.js)       │  │
                    │  └────────────────────────┘  │
                    └───────────────┬──────────────┘
                                    ▼
      ┌───────────┬───────────┬───────────┬──────────────┐
      │ PostgreSQL│  SQLite   │   MySQL   │   MongoDB    │
      │ /Supabase │ (dev/สอบ) │           │ (เอกสารฝัง)   │
      └───────────┴───────────┴───────────┴──────────────┘
```

**ทำไมเลือกแบบนี้**
- แยก frontend / API / database ออกจากกัน เปลี่ยนฐานข้อมูลได้โดยไม่ต้องแก้หน้าเว็บ
- ตรรกะการคิดเงินอยู่ที่ API ชั้นเดียว ป้องกันการแก้ราคาจากฝั่ง client
- ถ้าโหลดสูงขึ้น สามารถเพิ่ม instance ของ API ได้แบบ stateless (JWT ไม่ต้องเก็บ session)

## 3. เทคโนโลยีที่ใช้

| ชั้น | เทคโนโลยี | เหตุผล |
|---|---|---|
| Frontend | HTML + CSS + Vanilla JS | ไม่ต้อง build ขั้นตอนเดียวเปิดใช้ได้ทันที |
| Backend | Node.js + Express | เขียน JS ภาษาเดียวทั้งระบบ |
| Auth | JWT + bcrypt | stateless ขยายเซิร์ฟเวอร์ง่าย รหัสผ่านถูก hash |
| Database | PostgreSQL / Supabase (หลัก) | ธุรกรรม ACID จำเป็นกับการตัดสต๊อกและคิดเงิน |
| Deploy | Supabase + Render/Railway | ฟรีทีเออร์เพียงพอสำหรับโปรเจกต์เรียน |

## 4. Entity Relationship Diagram

```
customers 1───∞ addresses
    │1
    │
    ∞
  orders ∞───1 users (พนักงานที่รับออเดอร์)
    │1    ∞───1 promotions
    │     ∞───1 addresses
    ├──1:∞ order_items ∞───1 menu_items
    │         │1              │∞
    │         │               └──1 categories
    │         ∞
    │      order_item_toppings ∞───1 toppings
    ├──1:1 payments
    ├──1:1 deliveries ∞───1 users (rider)
    └──1:1 reviews

menu_items 1───∞ pizza_variants 1───∞ pizza_recipes ∞───1 ingredients
                                                          │1
                                                          └──∞ inventory_logs
```

**ความสัมพันธ์สำคัญ**
- `menu_items` เก็บ "ชื่อพิซซ่า" ส่วน `pizza_variants` เก็บ "ขนาด+ขอบ+ซอส+ราคา" — พิซซ่าหน้าเดียวมีได้หลายราคา
- `pizza_recipes` คือสะพานระหว่างเมนูกับสต๊อก ทำให้ตัดวัตถุดิบอัตโนมัติเมื่อขาย
- `order_items` เก็บ `unit_price` ไว้ในตัวเอง เพราะถ้าร้านขึ้นราคาทีหลัง ใบเสร็จเก่าต้องไม่เปลี่ยน

## 5. Flow การสั่งซื้อ (จุดที่ซับซ้อนที่สุด)

```
ลูกค้า            API                        Database
  │                │                            │
  │ POST /orders   │                            │
  ├───────────────►│                            │
  │                │  BEGIN TRANSACTION         │
  │                ├───────────────────────────►│
  │                │  1. ดึงราคาจริงของทุก variant│
  │                │  2. บวกราคาท็อปปิ้ง          │
  │                │  3. ตรวจโค้ดส่วนลด + ยอดขั้นต่ำ│
  │                │  4. INSERT orders           │
  │                │  5. INSERT order_items      │
  │                │  6. ลด ingredients ตามสูตร   │
  │                │  7. INSERT inventory_logs    │
  │                │  8. INSERT payments (unpaid) │
  │                │  9. บวกแต้มลูกค้า            │
  │                │  COMMIT (พลาดขั้นใด rollback)│
  │                │◄───────────────────────────┤
  │ 201 + order    │                            │
  │◄───────────────┤                            │
```

**ทำไมต้องเป็น transaction:** ถ้าตัดสต๊อกสำเร็จแต่บันทึกออเดอร์ล้มเหลว วัตถุดิบจะหายไปเฉย ๆ ระบบต้องยอมรับผลทั้งหมดหรือไม่ยอมรับเลย

## 6. สถานะออเดอร์

```
pending ──► preparing ──► ready ──┬──► delivering ──► completed
   │            │                 │                       ▲
   │            │                 └───────────────────────┘  (รับที่ร้าน)
   └────────────┴──► cancelled
```

ยกเลิกได้เฉพาะก่อนสถานะ `ready` และเมื่อยกเลิกควรคืนสต๊อก (จุดที่พัฒนาต่อได้)

## 7. ความปลอดภัย

| ประเด็น | วิธีรับมือ |
|---|---|
| รหัสผ่านรั่ว | เก็บเป็น bcrypt hash (cost 10) ไม่เก็บ plaintext |
| ปลอมสิทธิ์ | JWT เซ็นด้วย secret + ตรวจ role ทุก endpoint ที่แก้ข้อมูล |
| SQL Injection | ใช้ parameterized query (`$1`, `?`) ทุกที่ ไม่ต่อสตริง SQL |
| แก้ราคาจากหน้าเว็บ | ไม่รับ price จาก client — ดึงจาก DB มาคำนวณใหม่เสมอ |
| ข้อมูลลูกค้ารั่วผ่าน Supabase | เปิด Row Level Security ทุกตาราง (ดู `schema-supabase.sql`) |
| service key หลุด | เก็บใน `.env` เท่านั้น มี `.gitignore` กันไว้ ห้ามใส่ในไฟล์ frontend |

## 8. ประสิทธิภาพ

- ทำ index ที่ `orders(status)`, `orders(created_at)`, `order_items(order_id)` เพราะจอครัวและรายงานยิงคิวรีเหล่านี้บ่อยที่สุด
- ใช้ connection pool (max 10) แทนการเปิด connection ใหม่ทุก request
- รายงานยอดขายทำเป็น view (`v_daily_sales`) ให้ฐานข้อมูลคำนวณแทนที่จะดึงทุกแถวมานับใน Node

## 9. เปรียบเทียบฐานข้อมูลทั้ง 4 แบบในโปรเจกต์นี้

| | PostgreSQL/Supabase | SQLite | MySQL | MongoDB |
|---|---|---|---|---|
| ติดตั้ง | ต้องมี server / ใช้คลาวด์ | ไฟล์เดียว | ต้องมี server | ต้องมี server |
| Transaction | ครบถ้วน | ครบ (ไฟล์เดียว) | ครบ (InnoDB) | ต้องใช้ replica set |
| เขียนพร้อมกันหลายคน | ดีมาก | ล็อกทั้งไฟล์ | ดี | ดี |
| โครงสร้างข้อมูล | ตาราง + JSON | ตาราง | ตาราง | เอกสารฝังซ้อน |
| เหมาะกับ | ระบบจริง | ตอนพัฒนา/นำเสนอ | ระบบจริง งานทั่วไป | ข้อมูลรูปแบบไม่คงที่ |
| จุดอ่อนกับงานนี้ | – | ร้านหลายสาขาไม่ไหว | ไม่มี RETURNING | คุมความถูกต้องของสต๊อกยากกว่า |

**สรุปที่เลือก:** PostgreSQL ผ่าน Supabase เป็นหลัก เพราะการตัดสต๊อกและคิดเงินต้องการ transaction ที่เชื่อถือได้ ส่วน SQLite ใช้ตอนพัฒนาเพื่อไม่ต้องติดตั้งอะไรเพิ่ม

## 10. สิ่งที่พัฒนาต่อได้

- แจ้งเตือนออเดอร์ใหม่แบบเรียลไทม์ด้วย Supabase Realtime หรือ WebSocket
- คืนสต๊อกอัตโนมัติเมื่อยกเลิกออเดอร์
- ระบบหลายสาขา (เพิ่มตาราง `branches` แล้วผูกกับ `orders` และ `ingredients`)
- เชื่อม payment gateway จริง เช่น Omise หรือ PromptPay QR
